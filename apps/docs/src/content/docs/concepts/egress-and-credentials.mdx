OpenMA's design rule is that **the sandbox never holds a credential**: outbound requests still carry authentication, but the header is added by a resolver outside the sandbox's trust boundary — not by the agent, and not by anything the agent can read. Today that boundary is *enforced* only on the Cloudflare driver; on other drivers it is advisory or unsupported (table below). The design goal stands either way — a prompt-injected agent should have nothing to leak because no token lives in its address space. (`command_secret` credentials, which flow into the sandbox's per-command env, are the documented exception — see [Vault & MCP Credentials](/build/vault-and-mcp/).)

This page is the authoritative reference for how that works today: the port contract every runtime driver is measured against, what each driver actually enforces, and the one place `allowed_hosts` is currently applied.

## The credential-egress contract

`CredentialEgressPort` in `packages/runtime-resource-contract/src/credential-egress.ts` is the runtime-host lifecycle for sandbox credential access. It is an internal Port, not a Managed Agents API shape — clients never see it.

<Steps>

1. `capabilities(scope)` — reports the driver's `CredentialEgressCapabilities`: an enforcement tier, a credential mode, and the intercepted protocols.
2. `prepare({ scope, fence, requirement, idempotencyKey, signal })` — stages one egress grant and returns a `CredentialEgressBinding`, or `null` when no grant is needed.
3. `attach({ scope, fence, binding, sandbox, signal })` — wires the prepared grant into the acquired sandbox before the harness starts.
4. `revoke({ scope, fence, binding, reason })` — withdraws authorization **before** provider compute is stopped or retained. Reasons: `completed`, `failed`, `lease_lost`.
5. `release({ scope, fence, binding })` — idempotent cleanup after revoke.

</Steps>

Two properties make the binding safe to pass around:

- **It is scoped to the full runtime identity** — `(workspaceId, environmentId, sessionId, workId)` plus the resource fence's `ownerId` and monotonic `generation`. Copying a binding to another Session, runtime, or generation must fail.
- **It is not a secret.** `CredentialEgressBinding` is `{ bindingId, enforcement, credentialMode }` — an opaque identifier for one prepared grant. The vault token lives behind it, never in it, and the contract forbids persisting the binding into a sandbox lease or checkpoint.

### Enforcement tiers

Every driver advertises one `CredentialEgressEnforcement` level:

| Tier | Meaning | Valid for a `required` profile |
|---|---|---|
| `enforced` | Interception happens in the data path — the host or provider prevents direct bypass for the declared traffic class. The sandbox cannot route around it. | yes |
| `advisory` | Credentials are proxied for cooperating clients — proxy env vars like the `oma-vault` sidecar — but a determined process inside the sandbox can bypass the proxy and reach the network directly. | no |
| `unsupported` | The driver cannot inject credentials at the network layer; the Port is absent unless the operator injects a certified implementation. | no |

The credential mode says where the secret material lives:

| Mode | Meaning |
|---|---|
| `live` | The resolver reads the Vault credential at request time — a per-request lookup that survives token rotation without re-preparing the binding. |
| `snapshot` | Provider-side substitution receives a per-runtime copy of the credential. It cannot claim live-rotation semantics and must be revoked — or the runtime destroyed — on lease loss. |

A runtime profile declares `credentialEgress.requirement` as `required`, `best_effort`, or `disabled`. When the profile marks credential egress `required`, the provider registry throws `ManagedRuntimeCapabilityError` unless the driver descriptor advertises `enforcement: "enforced"` — and it re-checks the created Port's live `capabilities()` the same way before any compute is leased. See `packages/managed-runtime-host/src/provider-driver-registry.ts`.

## What each driver enforces today

Driver descriptors are the source of truth. Today **only the Cloudflare driver declares `enforced`**:

| Driver | Enforcement | Mode | Intercepted | Implementation |
|---|---|---|---|---|
| `managed-runtime-cloudflare` | `enforced` | `live` | `http`, `https` | `outboundByHost` interceptor in the agent worker; `attach` pins the runtime to the scope's tenant/environment/Session/Work and fence generation via `setOutboundContext` |
| `managed-runtime-node` (Node + Docker) | `unsupported` by default | `snapshot` | — | Descriptor defaults to `unsupported`; the self-host deployment layers the `oma-vault` sidecar on top, which is **advisory** — a bypassable env proxy, not a `required`-grade mechanism |
| `managed-runtime-cloudflare-bridge` | `unsupported` by default | `snapshot` | — | Descriptor default; operator may inject a certified Port via `options.credentialEgress` |
| `managed-runtime-e2b` | `unsupported` by default | `snapshot` | — | Descriptor default; hosted/BYOC egress features are not wired into the Port unless injected |
| `managed-runtime-daytona` | `unsupported` by default | `snapshot` | — | Descriptor default |
| `managed-runtime-boxlite` (LiteBox & BoxRun) | `unsupported` by default | `snapshot` | — | Descriptor default; BoxRun shares the managed BoxLite driver |
| `managed-runtime-blaxel` | `unsupported` by default | `snapshot` | — | Descriptor default |
| `managed-runtime-sprites` | `unsupported` by default | `snapshot` | — | Descriptor default |
| `managed-runtime-vercel` | `unsupported` by default | `snapshot` | — | Descriptor default; provider-side request transforms exist but are not certified as the Port |
| `managed-runtime-modal` | `unsupported` by default | `snapshot` | — | Descriptor default |
| `managed-runtime-superserve` | `unsupported` by default | `snapshot` | — | Descriptor default |

Two patterns to read from that table:

- **`unsupported` is a floor, not a wall.** Every generic adapter accepts a certified `CredentialEgressPort` through driver `options.credentialEgress`; several providers also ship native network policy or secret-substitution features (BoxLite `allowNet`, Blaxel proxy firewall, Vercel header transforms, Superserve secret proxy, Modal domain/CIDR allowlists) that a deployment can certify behind the Port.
- **Advisory is honest about bypass.** The `oma-vault` sidecar on Node/Docker is a mockttp HTTPS proxy plus a per-install local CA, configured through ordinary proxy environment variables. It injects credentials for cooperating clients, but nothing stops an in-sandbox process that ignores the env vars — so it is `advisory`, and a `required` profile will not accept it.

<Aside type="caution">
  Do not confuse credential egress with network egress. A stored `allowed_hosts` list or a provider network policy restricts *where* traffic can go; the credential-egress Port controls *how credentials reach* the traffic that is allowed. They compose, but neither substitutes for the other.
</Aside>

## How credentials flow on each host

Both production paths implement the same strip-match-inject-forward shape; only the Cloudflare path is enforced.

- **Cloudflare** — the agent worker's `outboundByHost` interceptor matches the request hostname against the Session's Vault credentials, strips inbound `Authorization` / `x-api-key` / `x-goog-api-key`, injects the matched credential, and forwards via `env.MAIN_MCP.outboundForward`.
- **Self-host (Node + Docker)** — `apps/oma-vault` runs a mockttp HTTPS proxy with a per-install self-signed CA. Sandboxes get `HTTPS_PROXY=http://oma-vault:14322` and trust the CA at startup; the proxy reads vault rows directly from the shared database and applies the same strip-match-inject-forward sequence.

On the main-worker path, `mcp_oauth` credentials additionally get 401-triggered refresh — the rotated tokens persist back to the Vault, so Sessions survive token rollover. The full resolver contract, including the audit trail and `command_secret` limits, is in [Vault & MCP Credentials](/build/vault-and-mcp/); the concept-level summary is the [Vault section](/concepts/#vault).

## `allowed_hosts` covers `web_fetch` only

When an Environment sets `networking.type: "limited"`, the `allowed_hosts` list is enforced inside the **`web_fetch` tool** — `assertWebFetchUrlAllowed` in `apps/agent/src/harness/web-fetch-http.ts`:

- Each request's hostname is checked against `allowed_hosts` with a suffix match: `host === a || host.endsWith('.' + a)` (normalized, so `allowed_hosts: ["example.com"]` also permits `api.example.com`).
- Redirects are followed manually and the check **re-runs on every hop**, up to 10 redirects — a redirect cannot bounce the agent onto an unlisted host.
- Only `http:` and `https:` URLs are allowed at all.

<Aside type="caution">
  `allowed_hosts` does **not** cover `bash`/`curl`, `web_search`, or MCP server traffic today. A sandboxed process can reach the network outside the `web_fetch` check unless the deployment layers its own egress policy (Cloudflare Internet policy, provider allowlists, Docker networking). Extending coverage is tracked in [issue #297](https://github.com/openma-ai/open-managed-agents/issues/297).
</Aside>

## What is planned, not implemented

A general egress allowlist proxy covering **all** sandbox traffic — every protocol, every tool — is planned but not implemented. Until it lands, combine the layers deliberately: `enforced` credential egress where you need `required`-grade isolation, `allowed_hosts` for `web_fetch`, and provider/network-level policy for everything else.
