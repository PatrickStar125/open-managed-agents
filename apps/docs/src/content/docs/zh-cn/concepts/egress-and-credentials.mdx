OpenMA 的规则一句话就能说完：**沙箱从不持有凭据**。出站请求仍然带着认证信息，但请求头是由沙箱信任边界之外的解析器加上的——不是 Agent，也不是 Agent 能读到的任何东西。被注入 prompt 的 Agent 没有凭据可泄漏，因为它的地址空间里根本没有凭据。

本页是这套机制的权威参考：每个运行时驱动都要对齐的 Port 契约、今天每个驱动实际的强制等级，以及 `allowed_hosts` 当前唯一生效的位置。

## 凭据出站契约

`CredentialEgressPort`（`packages/runtime-resource-contract/src/credential-egress.ts`）是运行时宿主侧的沙箱凭据访问生命周期。它是内部 Port，不是 Managed Agents API 的形状——客户端永远看不到它。

<Steps>

1. `capabilities(scope)` —— 报告驱动的 `CredentialEgressCapabilities`：一个强制等级、一种凭据模式，以及被拦截的协议列表。
2. `prepare({ scope, fence, requirement, idempotencyKey, signal })` —— 准备一份出站授权，返回 `CredentialEgressBinding`；不需要授权时返回 `null`。
3. `attach({ scope, fence, binding, sandbox, signal })` —— 在 Harness 启动前，把准备好的授权接入已获取的沙箱。
4. `revoke({ scope, fence, binding, reason })` —— 在 provider 计算被停止或保留**之前**撤销授权。原因：`completed`、`failed`、`lease_lost`。
5. `release({ scope, fence, binding })` —— revoke 之后的幂等清理。

</Steps>

两个性质让 binding 可以安全地传递：

- **它绑定到完整的运行时身份**——`(workspaceId, environmentId, sessionId, workId)`，外加资源 fence 的 `ownerId` 和单调递增的 `generation`。把 binding 复制到另一个 Session、运行时或 generation 必须失败。
- **它不是秘密。** `CredentialEgressBinding` 就是 `{ bindingId, enforcement, credentialMode }`——一份已准备授权的不透明标识符。Vault token 藏在它后面，从不在它里面；契约还禁止把 binding 持久化进沙箱租约或 checkpoint。

### 强制等级

每个驱动都声明一个 `CredentialEgressEnforcement` 等级：

| 等级 | 含义 | `required` profile 可用 |
|---|---|---|
| `enforced` | 拦截发生在数据路径上——host 或 provider 能阻止对声明流量类别的直接绕过。沙箱无法绕行。 | 是 |
| `advisory` | 只为配合的客户端代理凭据——比如 `oma-vault` sidecar 这类代理环境变量——但沙箱内一个有决心的进程可以绕过代理直接访问网络。 | 否 |
| `unsupported` | 驱动无法在网络层注入凭据；除非运维方注入经过认证的实现，否则该 Port 不存在。 | 否 |

凭据模式说明秘密材料放在哪里：

| 模式 | 含义 |
|---|---|
| `live` | 解析器在请求时实时读取 Vault 凭据——逐请求查找，token 轮换无需重新 prepare binding 即可存活。 |
| `snapshot` | provider 侧替换拿到一份按运行时的凭据副本。它不能声称实时轮换语义，且在租约丢失时必须被 revoke——或销毁运行时。 |

运行时 profile 把 `credentialEgress.requirement` 声明为 `required`、`best_effort` 或 `disabled`。当 profile 把凭据出站标记为 `required` 时，provider 注册表会抛出 `ManagedRuntimeCapabilityError`，除非驱动描述符声明了 `enforcement: "enforced"`——并且在出租任何计算之前，它还会用同样的方式复查已创建 Port 的实时 `capabilities()`。见 `packages/managed-runtime-host/src/provider-driver-registry.ts`。

## 今天每个驱动的实际强制等级

驱动描述符是事实来源。今天**只有 Cloudflare 驱动声明了 `enforced`**：

| 驱动 | 强制等级 | 模式 | 拦截协议 | 实现 |
|---|---|---|---|---|
| `managed-runtime-cloudflare` | `enforced` | `live` | `http`、`https` | Agent worker 内的 `outboundByHost` 拦截器；`attach` 通过 `setOutboundContext` 把运行时钉到 scope 的 tenant/environment/Session/Work 和 fence generation 上 |
| `managed-runtime-node`（Node + Docker） | 默认 `unsupported` | `snapshot` | — | 描述符默认为 `unsupported`；自托管部署在其上叠加 `oma-vault` sidecar，它是 **advisory** ——可绕过的环境变量代理，不是 `required` 级机制 |
| `managed-runtime-cloudflare-bridge` | 默认 `unsupported` | `snapshot` | — | 描述符默认；运维方可通过 `options.credentialEgress` 注入认证过的 Port |
| `managed-runtime-e2b` | 默认 `unsupported` | `snapshot` | — | 描述符默认；hosted/BYOC 的出站功能除非被注入，否则未接入 Port |
| `managed-runtime-daytona` | 默认 `unsupported` | `snapshot` | — | 描述符默认 |
| `managed-runtime-boxlite`（LiteBox 与 BoxRun） | 默认 `unsupported` | `snapshot` | — | 描述符默认；BoxRun 共用托管 BoxLite 驱动 |
| `managed-runtime-blaxel` | 默认 `unsupported` | `snapshot` | — | 描述符默认 |
| `managed-runtime-sprites` | 默认 `unsupported` | `snapshot` | — | 描述符默认 |
| `managed-runtime-vercel` | 默认 `unsupported` | `snapshot` | — | 描述符默认；provider 侧的请求 transform 存在，但未认证为 Port |
| `managed-runtime-modal` | 默认 `unsupported` | `snapshot` | — | 描述符默认 |
| `managed-runtime-superserve` | 默认 `unsupported` | `snapshot` | — | 描述符默认 |

从这张表里读出两个规律：

- **`unsupported` 是地板，不是天花板。** 每个通用适配器都接受通过驱动 `options.credentialEgress` 注入的认证 `CredentialEgressPort`；若干 provider 还自带网络策略或秘密替换能力（BoxLite `allowNet`、Blaxel 代理防火墙、Vercel 请求头 transform、Superserve 秘密代理、Modal 域名/CIDR 允许列表），部署可以把它们认证到 Port 后面。
- **advisory 对可绕过性是诚实的。** Node/Docker 上的 `oma-vault` sidecar 是一个 mockttp HTTPS 代理加每安装一份的自签 CA，通过普通的代理环境变量配置。它为配合的客户端注入凭据，但没有任何东西能阻止沙箱内忽略这些环境变量的进程——所以它是 `advisory`，`required` profile 不会接受它。

<Aside type="caution">
  不要把凭据出站和网络出站混为一谈。存下来的 `allowed_hosts` 列表或 provider 网络策略限制的是流量**能去哪**；凭据出站 Port 控制的是**凭据如何到达**被放行的流量。两者可以组合，但谁也不能替代谁。
</Aside>

## 每个 host 上的凭据流

两条生产路径实现的是同一个形状：剥掉客户端自带的认证头，匹配目标，注入真实凭据，转发。

- **Cloudflare** —— Agent worker 的 `outboundByHost` 拦截器把请求 hostname 与 Session 的 Vault 凭据匹配，剥掉入站的 `Authorization` / `x-api-key` / `x-goog-api-key`，注入匹配到的凭据，再经 `env.MAIN_MCP.outboundForward` 转发。
- **自托管（Node + Docker）** —— `apps/oma-vault` 运行一个带每安装一份自签 CA 的 mockttp HTTPS 代理。沙箱得到 `HTTPS_PROXY=http://oma-vault:14322` 并在启动时信任该 CA；代理直接从共享数据库读 Vault 行，执行同样的「剥离-匹配-注入-转发」序列。

`mcp_oauth` 凭据在解析器内部得到由 401 触发的刷新——轮换后的 token 写回 Vault，因此 Session 可以在 token 轮换后继续存活。完整的解析器契约（包括审计轨迹和 `command_secret` 的限制）见 [Vault 与 MCP 凭据](/build/vault-and-mcp/)；概念级摘要是 [Vault 一节](/concepts/#vault)。

## `allowed_hosts` 只覆盖 `web_fetch`

当 Environment 设置 `networking.type: "limited"` 时，`allowed_hosts` 列表在 **`web_fetch` 工具内部**强制执行——`apps/agent/src/harness/web-fetch-http.ts` 的 `assertWebFetchUrlAllowed`：

- 每个请求的 hostname 按后缀匹配 `allowed_hosts`：`host === a || host.endsWith('.' + a)`（先归一化，所以 `allowed_hosts: ["example.com"]` 也放行 `api.example.com`）。
- 重定向手动跟随，且**每一跳都重新检查**，最多 10 跳——重定向无法把 Agent 弹到未列出的主机上。
- 无论如何只允许 `http:` 和 `https:` 协议。

<Aside type="caution">
  `allowed_hosts` 今天**不**覆盖 `bash`/`curl`、`web_search` 或 MCP 服务器流量。除非部署自己叠加出站策略（Cloudflare Internet 策略、provider 允许列表、Docker 网络），否则沙箱进程可以绕过 `web_fetch` 检查访问网络。扩展覆盖范围见 [issue #297](https://github.com/openma-ai/open-managed-agents/issues/297)。
</Aside>

## 规划但未实现

覆盖**所有**沙箱流量的通用出站允许列表代理——每个协议、每个工具——在规划中，尚未实现。落地之前要有意识地组合各层：需要 `required` 级隔离时用 `enforced` 凭据出站，`web_fetch` 用 `allowed_hosts`，其余一切交给 provider/网络层策略。
